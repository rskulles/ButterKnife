# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ButterKnife is a .NET Blazor Web App (Server interactivity) for chatting with LLMs hosted on the local network (Ollama, LM Studio, vLLM, llama.cpp server) plus optional Anthropic. The LLM backends are *not* on this machine; every backend is reached over HTTP at a base URL stored in the app's SQLite database.

README.md is written for end users (why, download, connect a server) and deliberately avoids implementation detail; this file is the developer reference.

**Configuration** lives in `src/ButterKnife/appsettings.json` (override per environment file or with `Section__Key` environment variables):

| Section | Keys | Purpose |
|---|---|---|
| `Database` | `ConnectionString` | SQLite file; default `Data Source=data/butterknife.db`, relative to the content root (bundled builds redirect it, see "Releases and the bundled build"). |
| `Llm` | `Backends` | Seed connections, used only when the connections table is empty on first start. Empty in `appsettings.json`; `appsettings.Development.json` seeds two placeholders. |
| `Llm` | `DefaultPersona`, `AutoCompactThreshold`, `CompactKeepRecentTurns` | Persona preselected for new chats; compact when usage passes this fraction of the window (0 disables); turns kept verbatim after a compaction. |
| `Dictation` | `AutoStopOnSilence`, `AutoSendAfterTranscription`, `SilenceDurationMs`, `MaxRecordingSeconds` | Microphone defaults; each browser overrides the two toggles from the ⚙ beside the mic. |

API keys are protected with ASP.NET Core Data Protection. In development the key ring is in the user profile of the account running the app, so running as another user or on another machine makes stored keys read back empty (re-enter them); bundled builds keep the ring beside the database.

**Toolchain.** .NET SDK 10.0, target `net10.0`. `Directory.Build.props` sets `TreatWarningsAsErrors`, nullable and implicit usings for every project, so any analyzer warning fails the build. `.editorconfig` (LF, 4-space indent, 2 for json/yml/slnx) makes file-scoped namespaces and mandatory braces warnings and flags unused usings (IDE0005), all of which therefore fail the build. Client-side libraries are pinned by LibMan (`src/ButterKnife/libman.json`: Bootstrap 5.3.8 JS bundle only, Bootstrap Icons) but the restored files under `wwwroot/lib/` are **committed**, and nothing restores them at build time. Reason: the build-time restore (`Microsoft.Web.LibraryManager.Build`, since removed) ran after static-web-asset discovery on a clean machine, so CI-published builds copied the files but left them out of the endpoints manifest and `MapStaticAssets` returned 404 for the icon font. To update a library, change `libman.json`, run `dotnet tool restore` then `dotnet libman restore` from `src/ButterKnife`, and commit the result. The stylesheet is the Bootswatch "pulse" build committed at `wwwroot/bootstrap_pulse.min.css` (system font stack, no external fetches; the earlier "morph" `bootstrap*.css` files remain in `wwwroot` unreferenced). Icons in markup are `<i class="bi bi-...">`. Solution file is `ButterKnife.slnx` (XML solution format); projects are `src/ButterKnife` (web app) and `tests/ButterKnife.Tests` (xUnit 2.x: no `TestContext`, use `CancellationToken.None`).

## Commands

```bash
# Build / run (dotnet run uses the "http" launch profile: Development environment, http://localhost:5175)
dotnet build
dotnet run --project src/ButterKnife
dotnet watch --project src/ButterKnife        # hot reload during UI work

# Expose on the LAN (Kestrel binds to localhost only by default)
dotnet run --project src/ButterKnife --urls http://0.0.0.0:5175

# Tests
dotnet test
dotnet test --filter "FullyQualifiedName~OllamaClientTests"                       # one class
dotnet test --filter "FullyQualifiedName~OllamaClientTests.StreamsTokensFromNdjson" # one test

# Override seed backends without editing config (env vars use __ as the section separator; seed only, see Connections)
Llm__Backends__0__BaseUrl=http://127.0.0.1:11434 dotnet run --project src/ButterKnife

# Formatting (analyzers run as part of build; warnings are errors)
dotnet format
dotnet format --verify-no-changes

# Offline development against the stub server (see "Manual testing" below)
python3 tools/stub-llm-server.py --port 11434 --delay 0.08
```

## Architecture

**Render mode.** `App.razor` sets `InteractiveServerRenderMode(prerender: false)` on both `Routes` and `HeadOutlet`; `Program.cs` registers only `AddInteractiveServerComponents` / `AddInteractiveServerRenderMode`. Chat needs a live SignalR circuit for token streaming, so do not mix in WebAssembly or Auto modes; there is no client project. Prerendering is off on purpose: the chat page has nothing useful to show statically and prerendering would query every backend's model list twice per page load. The csproj sets `BlazorDisableThrowNavigationException`, so `NavigationManager.NavigateTo` during an interactive handler does not throw. `Components/Layout/ReconnectModal` is the template's reconnect dialog, wired to `Blazor.reconnect` / `resumeCircuit` in its collocated JS.

**DI.** Three extension methods are the only wiring: `Services/LlmServiceCollectionExtensions.AddLlmBackends` (binds and validates `LlmOptions` and `DictationOptions`, registers the shared `"llm"` HttpClient, registry, catalog, markdown renderer, compactor, transcription client/service, and the `ConnectionSeeder` hosted service), `Data/DataServiceCollectionExtensions.AddDataStores` (`DatabaseOptions`, `SqliteDatabase`, the six stores including `IUserStore` and `ICodeSessionStore`, `ConversationEvents`, `ConnectionEvents`, `SettingsEvents`, `PersonaEvents`, `UserEvents`, `CodeSessionEvents`) and `Services/AccountsServiceCollectionExtensions.AddAccounts` (cookie authentication, `LoginGate`, the scoped `CurrentUser`; see "Accounts" below). Options classes: `Options/LlmOptions` (`Backends` seed list, `DefaultPersona`, `AutoCompactThreshold`, `CompactKeepRecentTurns`; `BackendKind` is `Ollama` | `OpenAiCompatible` | `Anthropic` | `Transcription`), `Options/DictationOptions`, and `Data/DatabaseOptions` (lives in `Data/`, not `Options/`).

**Layering:**

- `Components/Pages/Chat.razor` (routes `/` and `/chat/{id}`): the chat page, markup and code in one file (the user's IDE copes badly with partial classes, so do not split it again). The `@code` block is sectioned by comment banners: core (state, lifecycle, selection, send/stream), images, context meter + compaction, dictation, and the nested `ChatTurn` transcript entry. The page holds conversation state for the circuit, renders messages, and appends streamed tokens in place via the mutable `ChatTurn` class. Its collocated `Chat.razor.js` module handles Enter-to-send, auto-scroll and dictation; Enter calls back into the component through a `DotNetObjectReference` (`[JSInvokable] SendFromKeyboardAsync`) rather than clicking the Send button, because that button is swapped for a Stop button while streaming and a captured element would go stale.
- **Code tab** (`Components/Pages/Code.razor`, routes `/code` and `/code/{id}`; markup and code in one file like the chat page): a Claude-Code-style agent for local models. **Who**: `CurrentUser.CanAdministerAsync` only (admin and not remote), checked by the page and by `NavMenu`, which shows a Chat / Code switch above the list for those users and lists the user's Code sessions (title over folder name, rename/delete menu) whenever the URL starts with `code`; the search box is chat-only. **Tool calling** is native in all three clients and opt-in per request: `ChatOptions.Tools` (an init-only property, never stored with a conversation's settings; `ToolDefinition(Name, Description, JsonElement Parameters)` in `Services/ToolCalling.cs`) puts the tools on the wire (Ollama and OpenAI-compatible `{"type":"function","function":{…}}`, Anthropic custom tools with the schema's `properties`/`required`). Completed calls arrive as `ChatDelta.ToolCall` (`ToolCall(Id, Name, Arguments)` with the raw JSON text) and the finish reason `FinishReason.ToolCalls`: Ollama sends calls whole (no id: one is made up; it still says `stop`, so the client reports `ToolCalls` when it saw any), OpenAI-compatible streams fragments by `index` that `ToolCallAssembler` joins and emits at `finish_reason` or the end of the stream, Anthropic sends `tool_use` blocks with `input_json_delta` emitted at `content_block_stop`. Going back, `ChatMessage.ToolCalls` on an assistant turn and `ChatRole.Tool` messages (`ToolCallId`, `ToolName`, `IsError`) become Ollama `tool_calls` (arguments as an object) + `role: tool` with `tool_name`, OpenAI `tool_calls` (arguments as a string) + `role: tool` with `tool_call_id`, Anthropic `tool_use` blocks + consecutive results merged into one user message of `tool_result` blocks. `ILlmClient.SupportsToolsAsync` (default interface method → null; `LlmClientBase` virtual) reads Ollama's `/api/show` `tools` capability and LM Studio's `tool_use` capability; Anthropic is always true; false disables Send with a warning. **Tools** (`Services/CodeTools.cs`, eight, kept few so the schemas stay cheap for small models): `read_file` (numbered lines, offset/limit, 1000 lines / 40k chars by default), `list_files` (one folder, or a glob: `**`, `{a,b}`, a pattern without `/` matches file names at any depth), `grep` (.NET regex, optional glob, 100 results), `edit_file` (exact unique `old_string` or `replace_all`; follows a CRLF file's line breaks; refuses if the file changed between preview and approval), `write_file`, `run_command` (in the session's shell, see below; `background: true` starts a command and returns after up to `BackgroundFirstOutput`, 3 s, with its first output and an id), `command_output` (what a background command printed since the last read, optionally waiting up to 60 s for something new, or `stop: true`) and `read_skill` (a skill's text by name, from wherever the skill lives). `CodeTools.Prepare` validates a call into a `ToolInvocation` (title, icon, `ToolPermission` None/Edit/Command, the edit's `LineDiff` computed up front so the user approves exactly what runs); bad arguments, unknown tools and paths outside the folder become an `Error` that goes back to the model as the tool's result. Local models are loose with types, so numbers and booleans written as strings are accepted. `Services/CodeWorkspace` resolves every path against the folder and refuses `..`, `~` and absolute paths elsewhere; search tools skip `IgnoredDirectories` (`.git`, `node_modules`, `bin`, `obj`, …) and hidden folders. **Pictures**: prompts take up to 6 images (the image button with an `InputFile`, or paste/drop through `Chat.razor.js`'s `wireImageInput` and `[JSInvokable] OnImagePasted`, re-encoded above 1.5 MB as a 1568 px JPEG like chat; anything that is not an image is refused, since the model reads project files itself), and `read_file` on a `.png/.jpg/.jpeg/.gif/.webp` (≤ `MaxImageFileBytes`, 5 MB) returns the picture as `ToolResult.Images`, which `CodeAgent.ResultMessage` puts on the tool message. Both are stored in `code_message_images` (BLOB, cascade on message delete) and shown as thumbnails that expand on click. On the wire, OpenAI-compatible servers accept images only on user messages and Ollama reads them there, so `ToolImages.MoveToUserMessages` (in `ToolCalling.cs`, called by both clients) strips them from tool messages and adds one user message ("The pictures returned by the tool calls above: …") after each run of results; Anthropic puts image blocks inside the `tool_result`. This only happens on the wire, so the stored history and compaction checkpoints never see the extra message. `SupportsImagesAsync` is probed with the tool and window checks: false (Ollama without `vision`, LM Studio `llm`) disables the image button, refuses pastes, and makes `CodeAgent.SupportsImages = false` turn every picture into `WithImagesAsText` notes; null (vLLM, llama.cpp) sends them and lets the server decide. Pictures count as `TokensPerImage` (about 4k chars) against the result budget, so old picture results are cleared like long text ("(a picture) was cleared"), and the summariser sees "[n image(s)]". **Shell** (`Services/CodeShell.cs`): `CodeShellRegistry` (singleton, `Program.cs`) keeps one `CodeShell` per Code session for the life of the process, so its state survives page reloads; `NavMenu`'s delete calls `Remove` and host shutdown disposes the registry, both of which kill the session's background commands (a crash can leave orphans). Every `run_command` is still its own process, but a wrapper (`PosixWrapper`; env vars `BK_CMD`/`BK_STATE`/`BK_CWD`/`BK_SAVE`, read into shell locals and unset before anything else so the snapshot never captures them) sources the previous `export -p` snapshot from the shell's temp state folder, `cd`s to the saved directory, `eval`s the command and then writes `pwd` (logical, not `-P`: macOS's `/var` → `/private/var` would otherwise look outside the project) and a fresh `export -p`. So `cd` and exported variables carry over like a terminal while timeouts and hung commands stay per process; shell-local variables, aliases and functions do not. On Windows (`PowerShellWrapper`) only the directory carries over. `ShellCommand.UnixShell` uses `$SHELL` only for POSIX shells (zsh, bash, sh, dash, ksh); fish and others fall back to zsh/bash. `BackgroundCommand`s (`bg1`, `bg2`, …; at most `MaxRunning` 8 running) start in the current directory with the same environment but save nothing, keep the last 200k chars of output, and track a read position so each `ReadNewAsync` returns only what is new. The system prompt tells the model about all this and lists the current directory (when not the project folder) and every background command with its status. The page subscribes to the shell's `Changed` (throttled to 2 renders/s) and shows a strip above the composer: one `<details>` per command (id, command, status, Stop or Dismiss) unfolding into its last 8k chars. `Services/ShellCommand` (`CreateStartInfo` + `RunAsync(ProcessStartInfo, …)`) runs through the user's login shell (`$SHELL -l -c`, so PATH matches their terminal even from the menu bar app; PowerShell on Windows), stdin closed, stdout+stderr merged, `PAGER=cat`/`NO_COLOR`, ButterKnife's own environment (`ASPNETCORE_*`, `BUTTERKNIFE_*`, `DOTNET_WATCH*`, anything with `__`) removed so a user's `dotnet run` does not inherit our port, whole process tree killed on timeout (default 120 s, max 600) or Stop, output clipped head+tail to 30k chars. **Loop** (`Services/CodeAgent.cs`): system prompt from `CodePrompt.Compose` (how to work, plan-mode note, folder, git or not, OS, shell, date, and the folder's `AGENTS.md`, `CLAUDE.md` or `.github/copilot-instructions.md`, first found, ≤ 20k chars), stream, run each call (asking through `ICodeAgentObserver.RequestPermissionAsync` when `NeedsPermission`), append results, repeat until a reply has no calls (`CodeTurnEnd.Done`), the user denies (`Denied`: every remaining call in that reply gets a "not run" result and the model is not asked again) or `MaxSteps` (40). `CodePermissionMode`: Ask (edits and commands ask), AcceptEdits (commands ask), Plan (edit tools not offered, prompt says plan only), Auto (nothing asks; the page shows a warning). "Always" on an edit switches the session to AcceptEdits; on a command it remembers `CommandPrefix` (program plus subcommand, e.g. `dotnet build`), and `IsCoveredBy` never lets a prefix cover a command with `;`, `&&`, `|`, redirection or `$(`. Inline `<think>` text goes through `ThinkTagSplitter`. `CodeAgent.Repair` gives every unanswered call a result (and drops stray results) before each turn, because OpenAI-style servers and Anthropic reject a call without one; the page also stores those results after a Stop. **Context** (`Services/CodeCompactor.cs`, wire-only like chat compaction: the stored transcript never changes). Every request sends the history after the checkpoint (`RequestTail`) with old tool results cleared (`ClipOldResults`): counting from the newest, once the long results (> `ClipMinChars`, 400) add up to more than half the window in characters (`ResultBudget`; `FallbackWindow` 32k when the window is unknown), older ones become a one-line "cleared, call the tool again" note; the latest step's results are always kept and the call stays, so pairs stay intact. Old edits are shrunk too (`ShrinkOldEdits`): a `write_file`/`edit_file` call before the latest step whose result was a success keeps its path and other fields, but each long `content`/`old_string`/`new_string` becomes "[n characters, m lines; left out …]", still valid JSON in the tool's shape (failed calls keep their text so the model can see what it tried). `TokenEstimator` counts tool-call arguments. Before each step `CodeAgent.PrepareRequestAsync` estimates the request (the larger of ~4 chars/token over messages + tool schemas, and `LastUsage`, the server's last prompt + completion count, plus what was added since); at `Llm:AutoCompactThreshold` (0.8) of a known `ContextWindow` it compacts (`CodeCompactor.CompactAsync`: the session's model, no tools, summarises from the checkpoint up to the next one, `FindCheckpoint`) and if still over, clears every result but the latest step's. **Checkpoints** are boundaries (`IsBoundary`): a user message, or an assistant message right after the results of a step whose calls are all answered; never between a call and its result. `FindCheckpoint` picks the user message that starts the last `KeepRecentPrompts` prompts (`Llm:CompactKeepRecentTurns` / 2, since that option counts chat messages); when fewer prompts than that follow the checkpoint, only the last turn stays: its prompt, or, when that turn has at least `KeepRecentSteps` (2) step boundaries after its first step, the step that starts its last two; when the checkpoint is already inside the turn and fewer steps follow, the latest step (the one whose results the model has not seen) is all that stays. Null when nothing can move, so one long prompt with many steps compacts mid-turn. After a checkpoint inside a turn, `RequestTail` sends the turn's prompt again as the first message with `ResentNote` appended (Anthropic and many chat templates need a user message first, and the model keeps the task); the stored prompt is unchanged. The summariser sees user text, assistant text, each call with its arguments (300 chars) and each result's head and tail (800 chars, shrinking to fit 60% of the window, then the middle cut), inline `<think>` stripped, and is told the session may stop mid-request; a failure is reported once (`OnCompactionFailed`) and the turn carries on. The summary goes at the end of `CodePrompt.Compose(…, summary)` under `SummaryPreamble`. `code_sessions.summary_through` is still the number of leading messages covered; `CodeCompactor.StartOf` moves a checkpoint that is not a boundary (a transcript `Repair` changed) back to the boundary before it, so the tail always passes `Repair` unchanged. Observer: `OnCompacting` (spinner line in the transcript), `OnCompactedAsync(CodeCompaction(Summary, Through))` (stored with `SetSummaryAsync`, exact token count reset). The header's Compact button does the same on demand (Stop/Esc cancels; disabled when `FindCheckpoint` is null) and the transcript shows a dashed `.code-checkpoint` divider before the first entry at or after `StartOf(summary_through)` (prompts, replies and tool rows all carry `CodeItem.MessageIndex`), unfolding the summary. **Storage**: `code_sessions` (user, title, workspace path, connection id, model, permission mode, context usage, `summary`/`summary_through` added by migration) and `code_messages` (role, content, reasoning, `tool_calls` JSON, `tool_call_id`, `tool_name`, `is_error`, `diff` as unified lines for display, model, stats) via `ICodeSessionStore`/`SqliteCodeSessionStore`; deleting a user deletes their sessions; `CodeSessionEvents` refreshes the sidebar. **Page**: the folder (fixed once the session exists) comes from an inline picker that browses this computer's folders (`CodeWorkspace.ListFolders`, path box accepts `~`, recent folders from `RecentWorkspacesAsync`; a new session starts in the most recent one); the first send creates the session (title from the prompt, then `ChatTitler` after the first finished turn) and navigates with `replace: true`. The transcript shows prompts as bubbles, replies as full-width Markdown, and each call as a one-line `<details>` row (icon, title, `+n −m`, spinner/✓/✗/"declined") that unfolds into its diff or output; a call waiting for approval is a highlighted card with the diff or command, Allow / Always / Deny and an optional "tell the model what to do instead" box sent with Deny. Rows are matched to calls by the latest row with that id, because some servers number calls per request. Command output streams into its row while it runs. The page imports `Chat.razor.js` for Enter-to-send (`SendFromKeyboardAsync`), Esc to stop and ⌘⇧O for a new session (`OnShortcutAsync`), sticky scrolling and code highlighting. A model window under 16k gets a hint to raise the connection's context window. Markdown and reasoning styles shared by both pages live in `wwwroot/app.css` (which also gives `.page > main` `min-width: 0`, so a long unbroken line such as a command truncates instead of widening the page); the Code page's own (diff rows, output boxes) in `Code.razor.css`. A turn runs inside the page's circuit: leaving the page or closing the tab stops it, like a chat reply. **Slash commands and skills** (`Services/CodeCommands.cs`, Claude Code's file layout so existing ones work): `CodeCommands.TryParse` recognises `/name args` (a name followed by `/`, as in `/etc/hosts`, is plain text). Built-ins: `/init` (an ordinary turn with `InitPrompt`: explore and write or improve `AGENTS.md`, through the usual edit permission), `/clear` (new session, which starts in the same folder), `/compact` (the Compact button) and `/help` (commands and skills listed in the transcript, neither stored nor sent). Command files are Markdown under `.butterknife/commands/` or `.claude/commands/` in the project, then the same folders in the home directory (personal); the file name is the command, a sub-folder becomes a `folder:name` prefix, optional front matter gives `description` (else the body's first line), and `Expand` replaces `$ARGUMENTS` with what follows the command (or appends it). Built-ins cannot be shadowed and a project command beats a personal one. Commands are re-read from disk on every send so an edited file takes effect at once. The model gets the expansion as the user message, while `code_messages.display` keeps what was typed (`AppendAsync(display:)`, `CodeEntry.Display`); the bubble shows the typed command in monospace with a "What the model was sent" fold-out. Typing `/` opens a suggestion list above the composer (`MenuItems`: built-ins first, then files, filtered by prefix; arrows move, Enter on a partial name fills in the highlighted command, Enter again sends, Esc closes via `OnShortcutAsync("stop")`). Skills are folders with a `SKILL.md` under `.butterknife/skills/` or `.claude/skills/` in the project, then the same folders in the home directory, then the **built-in** ones in `src/ButterKnife/Skills/<name>/SKILL.md` (embedded resources named `ButterKnife.Skills/<name>/SKILL.md` by a csproj `EmbeddedResource` item, so single-file and `.app` builds need no extra files; `CodeCommands.BuiltInSkills` reads them once). The first to claim a name wins, so a project or personal skill with a built-in's name replaces it. `DiscoverSkills` takes `name`/`description` from front matter (folder name and first line otherwise), at most 30; `CodePrompt.Compose` lists names and descriptions only, and the model calls the `read_skill` tool for the text (`FindSkill`), which works for home-folder and built-in skills that `read_file` could not reach. The built-ins are written for small local models: short numbered steps using the tool names, ending with what to report: `explore-project`, `implement-feature`, `debug-issue`, `fix-failing-tests`, `write-tests`, `refactor`, `review-changes`, `git-commit`, `write-docs`, `security-review`. Edit them as plain Markdown; `CodeCommandsTests.BuiltInSkillsShipWithTheApp` lists the expected names.
- **Settings** (`Components/Pages/Settings.razor`, routes `/settings`, `/settings/{Section}` and the legacy `/connections`) uses its own `Components/Layout/SettingsLayout.razor`, which replaces the chat sidebar with a section list (General, Account, Connections, Personas, Users, Data; everyone sees Account, the rest only administrators, and `Settings.razor` answers "Administrators only" to a plain user who types an admin URL and defaults them to Account), a "Back to chat" link and the theme toggle; the frame CSS (`.page`, `.sidebar`, `main`) is shared with `MainLayout` from `wwwroot/app.css`. Sections are components under `Components/Settings/`: `GeneralSettings.razor` (release check, LAN switch, keyboard shortcuts, Quit), `AccountSettings.razor` (the signed-in user's display name, username, password, sign-out), `UsersSettings.razor` (administrators: list, add, reset password, toggle admin, delete), `ConnectionsSettings.razor` + `.razor.cs` code-behind (the connections table refuses a duplicate name and confirms a delete inline; the URL column never wraps and the two minor columns hide below `lg`), `PersonasSettings.razor` and `DataSettings.razor`. App-wide settings are rows in the `settings` table via `Data/ISettingsStore` (`SqliteSettingsStore`; blank value deletes the row), keys and defaults in `SettingKeys`; `SettingsEvents` is the in-process change signal. The label above the user's messages is the user's own display name (`AppUser.DisplayName`, default "User"), refreshed through `UserEvents`; `SettingKeys.UserDisplayName` survives only as the legacy key the migration reads.
- **Accounts** (replaced the earlier single network PIN). Users are rows in `users` (`Data/AppUser`, `IUserStore`, `SqliteUserStore`): username (unique, `COLLATE NOCASE`, 2–32 chars of letters/digits/`.`/`_`/`-`), display name (≤ 40), optional salted PBKDF2-SHA256 password hash (`Services/PasswordHasher`, 100 000 iterations, 4–64 chars), `is_admin`, `is_owner` and a random `security_stamp`. Every conversation carries `user_id`. The **owner** is the account this computer uses: `SqliteDatabase.EnsureOwnerAsync` creates it once (username `owner`, display name from the legacy `user.display_name` setting or "User", admin), gives every conversation without a `user_id` to it (old databases, restored old backups) and deletes the legacy display-name and PIN settings rows; it cannot be deleted or demoted and may have no password. Who a request is: `Services/LoginMiddleware` (`Program.cs`, after `UseAuthentication`, before antiforgery and the endpoints) makes any request from a loopback address without a sign-in the owner (`LoginGate.LocalPrincipalAsync`, claim `butterknife:local`; this is also the recovery path, so behind a reverse proxy on the same machine everyone would be the owner without forwarded headers), lets authenticated requests and `LoginGate.IsExempt` paths (`/login`, `/logout`, anything with a file extension) through, redirects other page requests (GET accepting HTML) to `/login?returnUrl=…` and answers everything else (`/_blazor`, `/backup`, posts) with 401. Other devices sign in on `/login` (`LoginEndpoints.MapLogin`: a self-contained HTML form like the old unlock page, no circuit) and get ASP.NET Core cookie authentication (`AccountsServiceCollectionExtensions.AddAccounts`: cookie `butterknife.session`, 30 days sliding, HttpOnly, SameSite Lax, Secure when the request is https, Data Protection keys) whose principal carries `NameIdentifier`, `Name`, the `admin` role and the stamp (`LoginGate.CreatePrincipal`); `OnValidatePrincipal` rejects a cookie whose user is gone or whose stamp changed (`LoginGate.IsCurrentAsync`). An admin resetting someone's password, a role change or a deletion rotates the stamp (signs that user's devices out); changing one's own password under Account does not. `TryLoginAsync` counts failures per address: five wrong tries lock that address out for a minute. `POST /logout` signs the cookie out (the sidebar and Account show "Sign out" only for non-local sessions). **Where** a request comes from matters too: the middleware stamps every signed-in request with a `NetworkZone` claim (`butterknife:zone`, `LoginGate.ZoneOf(IPAddress)`): `Local` for loopback, `Lan` for RFC 1918, link-local and IPv6 unique-local addresses, `Remote` for everything else, deliberately including Tailscale's `100.64.0.0/10`. The stamp is per request (`StampZone` replaces an older claim), never part of the sign-in, so a laptop that leaves the house is remote on its next page load; a Blazor circuit keeps the zone of the connection that opened it until the page reloads. `LoginGate.CanAdminister` = admin role **and** zone ≠ Remote: administrators administer only from inside the house, and a remote administrator chats and manages their account like anyone else. Blazor side: the circuit's principal comes from the connection (`ServerAuthenticationStateProvider`), and the scoped `Services/CurrentUser` re-reads the `AppUser` from the store per call (`GetAsync`, `IsLocalAsync`, `ZoneAsync`, `CanAdministerAsync`); `Chat.razor`, `NavMenu`, `SettingsLayout`, `Settings.razor`, `PhoneLink` and the settings sections use it, and a null user (deleted mid-session) sends the browser to `/login` with `forceLoad`. The server-wide sections (General, Connections, Personas, Users, Data) and the `/backup` endpoint (403 otherwise) need `CanAdminister`; `Settings.razor` tells a remote administrator "Only from home" and a plain user "Administrators only"; everyone has Account, which also says where the session is connected from. Do not put `tailscale serve`, Funnel or any other same-machine proxy in front of the app: proxied requests arrive from loopback and would all be the owner (forwarded headers are not honoured). Tailnet devices should open the machine's tailnet address directly with the LAN switch on. "Open on phone" warns when the current user has no password yet, since the phone has to sign in. Tests: `LoginGateTests` (hashing, lockout, principals and stamps, exemptions, return URLs, middleware with a `DefaultHttpContext` and a fake store) and `SqliteUserStoreTests` (owner seeding and legacy migration, uniqueness, passwords, stamps, delete cascade, per-user chat scoping).

- **Images.** `ChatMessage.Images` holds `ChatImage(MediaType, byte[])` attachments; they are stored in `message_images` (BLOB, cascade on message delete) and re-sent with their message on every turn, so the model sees them in context. Each client encodes them natively: Ollama `images` (raw base64 array on the message), OpenAI-compatible `content` parts (`image_url` data URL, text part first), Anthropic `ImageBlockParam` with a base64 source before the text block. Text-only messages keep `content` as a plain string for compatibility. On the wire `ChatMessage.WithFilesAsText()` prepends each file as `<document name="…">…</document>` to the content, the same for every backend (`ToRequestMessage` applies it before `WithImagesAsText`); the token estimate counts the text; the compaction request quotes the first 1500 chars of each document; the export lists attachments. A text-only model still takes files, only images are blocked. PdfPig (Apache 2.0) is listed in the notices file; the stub server logs how many documents a user message carries.
- **Context meter.** `StreamChatAsync` yields `ChatDelta` items: text deltas plus, when the backend reports it, a final `TokenUsage` (Ollama `prompt_eval_count`/`eval_count` on the done chunk; OpenAI-compatible via `stream_options.include_usage` on the last chunk; Anthropic `message_start.usage.input_tokens` + `message_delta.usage.output_tokens`). `GetContextWindowAsync(model)` returns the window or null: Ollama `/api/ps` `context_length` (what a loaded model actually runs with) then `/api/show` `*.context_length`; LM Studio's native `/api/v0/models/{id}` `max_context_length` at the server root; Anthropic Models API `max_input_tokens`. A connection's `ContextWindow` overrides all of that and is sent to Ollama as `options.num_ctx`. `Chat.razor` shows exact usage after a reply (prompt + completion) and a `TokenEstimator` estimate (~4 chars/token, ~1000/image) while typing or before the first reply; values persist on the conversation (`context_tokens`, `context_window`).
- **Compaction** (`Services/ConversationCompactor`) is client-side and backend-agnostic: the model summarises everything older than the last `Llm:CompactKeepRecentTurns` (default 4) turns; the summary is stored on the conversation (`summary`, `summary_through` = number of leading messages it covers) and `ComposeSystemPrompt` folds it into the system prompt of later requests, which then carry only the turns after the checkpoint. The stored transcript is never modified. Auto-compaction runs after a reply when reported usage ≥ `Llm:AutoCompactThreshold` (default 0.8, 0 disables) of a known window; the Compact button does the same on demand. **Key constraints:**

- HTTP-based clients go through the `IHttpClientFactory` named client `"llm"`; never `new HttpClient()`. Clients call `CreateClient` per request (not cached) so handler rotation keeps working. Timeout is `Timeout.InfiniteTimeSpan`; cancellation comes only from the caller's `CancellationToken`.
- Request bodies are serialised to a `StringContent` up front so they carry a `Content-Length`; some thin proxies and minimal servers cannot read chunked request bodies.
- Streaming must honour cancellation. The `CancellationToken` passed into `ILlmClient` is tied to the user's "Stop" button and to circuit disconnect; every `await` in the streaming path must forward it.
- Colour mode is Bootstrap's `data-bs-theme` on `<html>`, applied by an inline script in `App.razor` before the stylesheets load (choice in `localStorage` key `butterknife.theme`: `light` | `dark` | `auto`; `window.butterKnifeTheme.get/set`). `Components/Shared/ThemeToggle.razor` is the UI, placed in the sidebar footer beside the Settings link (`NavMenu.razor`) and in the settings layout's footer; there is no top bar in either layout. All app CSS must use Bootstrap variables (`var(--bs-...)`) rather than literal colours so both modes work; the template's hardcoded overrides in `wwwroot/app.css` were removed for that reason. Prefer Bootstrap utility classes over new custom CSS.
- Scoped CSS (`*.razor.css`) does not reach elements rendered by child components such as `NavLink`; use `::deep` for those (see `NavMenu.razor.css`).
- Blazor Server UI updates from a streaming loop must call `InvokeAsync(StateHasChanged)`. `Chat.razor` throttles to one render per 50 ms (`RenderInterval`) rather than re-rendering on every token.
- Conversations are persisted server-side through `Data/IConversationStore` (SQLite via `SqliteConversationStore`, plain ADO.NET) and belong to one user: `CreateAsync(userId, …)`, `GetAsync(id, userId)` (null for someone else's chat, which `Chat.razor` turns into a redirect to `/`), `ListAsync(userId)` and `SearchAsync(userId, query, limit)` all take the user's id, `BranchAsync` keeps the source's owner, and `Conversation.UserId` reports it. Message-level methods take only ids the page already loaded under that user. The `backend` column holds the **connection id** (GUID string); rows from before connections existed hold a name and resolve to `Guid.Empty`, so the chat shows "model no longer available" until the user picks one. The DB path comes from `Database:ConnectionString` (default `Data Source=data/butterknife.db`, relative to the content root). On case-insensitive filesystems (macOS, Windows) `data/` **is** the `Data/` source folder, so `.gitignore` excludes `src/ButterKnife/data/*.db*` by file rather than the folder; a folder rule silently hides new `Data/*.cs` files from `git status`. `Chat.razor` serves both `/` and `/chat/{id}`: the first send creates the conversation and navigates to its URL with `replace: true`, and `OnParametersSetAsync` reloads only when the id actually changes. Load order matters: `OnInitializedAsync` awaits only local data (personas, the current user, the image connection) and starts the model list in the background (`RefreshModelsInBackgroundAsync`), because `ModelCatalog` waits on every connection and a dead one blocks for the TCP connect timeout; the transcript therefore renders first with the saved model key selected, and `ReconcileSelection` (called when the list lands and on conversation load) swaps in the default with a note if that model no longer exists. While the list is empty the picker binds the placeholder option rather than the saved key. The user message is saved before the request goes out; the assistant reply (or the partial text after Stop / disconnect) is saved when streaming ends. `ConversationEvents` is an in-process singleton the sidebar (`NavMenu.razor`) and chat page subscribe to so the list refreshes across circuits. **Search** (box at the top of the sidebar): `SqliteDatabase.EnsureSearchIndexAsync` creates an external-content FTS5 table `messages_fts` over `messages.content` (unicode61, diacritics removed) with insert/delete/update triggers, and rebuilds it once for a database that predates it. `IConversationStore.SearchAsync(query, limit)` runs `BuildFtsQuery` (every word quoted and prefix-matched, all required) ordered by `bm25`, with `snippet()` wrapping matches in `SearchHit.MarkStart/MarkEnd` control characters, plus a `LIKE` substring match on titles (hits with a null `MessageId`). `NavMenu` debounces 250 ms, shows hits grouped by conversation with the markers rendered as `<mark>`, and links each to `chat/{id}?m={messageId}`; `Chat.razor` takes `m` as `[SupplyParameterFromQuery]`, remembers it across the load, and after the render calls `scrollToMessage` (unpins auto-scroll, scrolls the bubble into view, flashes `.msg-highlight`). User bubbles carry `data-message-id` too. Escape clears the box. **Pin and archive**: `conversations.pinned`/`archived` flags (`SetPinnedAsync`/`SetArchivedAsync`, no `updated_at` touch), `ListAsync` orders pinned first then newest, `ConversationSummary` carries both flags; the sidebar row (a `RenderFragment<ConversationSummary>` in `NavMenu.razor`) has a Bootstrap dropdown (`data-bs-popper-config` fixed strategy so the scrolling list does not clip it) with Pin/Rename/Archive/Delete, and archived chats sit under a folded "Archived (n)" toggle at the end of the list.
- System prompts come from **personas** (`Data/Persona`, `IPersonaStore`, `SqlitePersonaStore`). A conversation stores only `persona_id`; the persona's prompt is looked up at request time and prepended as a `ChatRole.System` message, never stored as a message row and never shown in the transcript. Built-in personas live in `DefaultPersonas.All` with **stable ids** (never change or reuse one) and are seeded with `INSERT OR IGNORE`, so users can edit them and edits survive restarts; they cannot be deleted. Custom personas are ordinary rows (`is_builtin = 0`) and deleting one sets `persona_id` to NULL on its conversations. `Llm:DefaultPersona` names the persona preselected for new chats. Settings → Personas (`Components/Settings/PersonasSettings.razor`, `/settings/personas`) lists them (built-in/custom badges), adds custom ones, edits any (a built-in whose text differs from `DefaultPersonas.All` offers "Restore original"), and deletes custom ones after an inline confirmation; `Data/PersonaEvents` tells open chat pages to reload their picker (a chat whose persona was deleted drops to none, matching what the store did to the row).
- `SqliteDatabase` owns the connection string, schema creation (`CREATE TABLE IF NOT EXISTS`), seeding (personas, the owner account via `EnsureOwnerAsync`) and forward-only migrations: columns added after first release go through `AddColumnIfMissingAsync`, never by editing the `CREATE TABLE` (new tables, such as `users`, may be added to it since `IF NOT EXISTS` covers them; an index on a migrated column is created after the `ALTER`). All stores take it by constructor and open a connection per operation. Circuit state holds only what the page is showing; everything durable goes through a store.
- `Llm:Backends` in `appsettings*.json` only seeds an empty database; keep committed defaults to placeholders like `http://ollama.local:11434`. `appsettings.Development.json` *replaces* the `Backends` array index-by-index, it does not merge.
- The app is intended to be reachable from other devices on the LAN. The Settings switch above or `--urls`/`ASPNETCORE_URLS` bind to `0.0.0.0`; the SignalR circuit requires WebSockets, so any reverse proxy in front must forward `Upgrade` headers. Browser microphone access needs a secure context, so dictation from another device needs TLS.

`tests/ButterKnife.Tests` is xUnit with no web host. Conventions worth reusing:

## Releases and the bundled build

`dotnet publish -r <rid>` produces a self-contained single-file executable (csproj `PropertyGroup` conditioned on `RuntimeIdentifier`: `SelfContained`, `PublishSingleFile`; trimming stays off because Blazor Server and the SDKs use reflection). `EnableCompressionInSingleFile` is on for Windows and Linux but **off for macOS**: with the hardened runtime on macOS 26 a compressed bundle dies with AccessViolations in framework code (R2R images decompressed into anonymous executable memory lose execute permission on thread-pool threads) on the first browser load, reproduced 11 of 12 launches against 0 of 6 uncompressed using `tools/browser-sim.py` (page + parallel assets + SignalR websocket); the `.dmg` is compressed so the download size is unchanged. Do not turn it back on for macOS without re-running that test on a Developer-ID-signed build. `IncludeNativeLibrariesForSelfExtract` is deliberately **false**: SQLite's `e_sqlite3` native library is published beside the executable (`libe_sqlite3.dylib` / `e_sqlite3.dll` / `libe_sqlite3.so`) instead of being extracted to `~/.net/<app>/<id>/` on first start. Extraction is shared by every copy of the same build and an interrupted first launch leaves it corrupt, after which every start dies with an AccessViolation in the thread pool (reproduced with kill -9 during start-up); shipping the file also lets it be signed and notarized with the bundle. `tools/make-macos-app.sh` copies `*.dylib` into `Contents/MacOS` and the workflow signs them; the Windows signing step's filter is `exe,dll`. `Services/DesktopLauncher` detects that bundle at runtime (`Assembly.Location` is empty in a single-file app; IL3000 is suppressed on that line on purpose) and only then: makes `AppContext.BaseDirectory` the content root so `wwwroot/` and `data/` sit beside the executable, persists Data Protection keys to `data/keys` (DPAPI-wrapped on Windows) so stored API keys survive moving the folder, defaults the listen address to `http://localhost:5175` when nothing is configured (5000 collides with macOS AirPlay), logs the local and LAN URLs, and opens the browser unless `BUTTERKNIFE_NO_BROWSER` is set. `dotnet run` never takes that path, so the development database stays in `src/ButterKnife/data/`. `appsettings.json` seeds no connections; only `appsettings.Development.json` does. On macOS the release is a `.app` built by `tools/make-macos-app.sh` from the publish folder: executable in `Contents/MacOS`, `wwwroot`/`appsettings.json`/static-assets manifest in `Contents/Resources` (`DesktopLauncher.IsMacAppBundle` detects the `Contents/MacOS` location and points the content root, the static-assets manifest path passed to `MapStaticAssets`, and the data directory accordingly). A signed bundle must never be written to, so in a `.app` the database and key ring live in `~/Library/Application Support/ButterKnife`. `Info.plist` sets `LSUIElement` (starts as a menu bar item), `NSMicrophoneUsageDescription` and ATS `NSAllowsLocalNetworking` (the window loads plain-http localhost), and names `ButterKnifeMenu` as the main executable: a Swift helper (`packaging/macos/ButterKnifeMenu/*.swift`, compiled together by the script with `swiftc -target <arch>-apple-macos12.0 -framework AppKit -framework WebKit`; signed with `packaging/macos/app-entitlements.plist`, which grants `device.audio-input` so dictation works under the hardened runtime) that launches `Contents/MacOS/ButterKnife` with `BUTTERKNIFE_NO_BROWSER=1`, tails its stdout into `~/Library/Logs/ButterKnife/server.log`, parses the "ButterKnife is running at X (on your network: Y)" line for the window and the Copy-address item. **The app window** (`AppWindow.swift`, `AppWindowController`): the UI in a `WKWebView` instead of a browser tab, shown at launch with a "Starting…" page until the address arrives (unless the helper itself was started with `BUTTERKNIFE_NO_BROWSER`). Showing it switches the activation policy to `.regular` (Dock icon, the menus from `AppMenus`: About, Settings… ⌘, (Blazor `navigateTo`, no reload), Hide, Quit; File: New Chat ⌘N, New Code Session ⇧⌘N, Open in Browser ⌥⌘O, Close ⌘W; Edit through the responder chain; View: Reload ⌘R, zoom ⌘0/⌘=/⌘- (`pageZoom`, kept in UserDefaults), full screen; Window); closing only hides it and drops back to `.accessory`, so the page and any running turn stay alive, and the Dock icon, ⌘O in the status menu or reopening the app shows it again. There is no back navigation: no back-swipe, Back/Forward and open-in-new-window removed from the context menu (`ButterKnifeWebView`), mouse side buttons swallowed. Navigation outside the server's origin (localhost/127.0.0.1/::1 count as one host) opens in the default browser, `target=_blank` included; `<a download>` and unshowable responses become `WKDownload`s saved through an `NSSavePanel` that starts in Downloads; file inputs get an `NSOpenPanel`; microphone requests from our own origin are granted (macOS still asks once). A page that fails to load (server starting or restarting) shows "Waiting for ButterKnife…" and retries every second up to 20 times. `isInspectable` is on (Safari's Develop menu). The status menu keeps Open in Browser and Copy address for phone; sends SIGTERM (then SIGKILL after 5 s) on Quit, routes SIGTERM/SIGINT/SIGHUP to itself through the same quit, and exits when the server exits on its own. It also passes `BUTTERKNIFE_PARENT_PID`; `DesktopLauncher.WatchParent` polls that pid every 2 s and stops the host if it vanishes, so a crashed helper cannot leave an orphaned server. **Windows** release builds are the same project compiled under `net10.0-windows` (csproj group conditioned on a `win*` RID: `UseWindowsForms`, `OutputType WinExe`, `EnableWindowsTargeting` so Linux CI can build it); `Services/WindowsTray.cs` is inside `#if WINDOWS` and pumps a `NotifyIcon` (Open, Copy address, Quit) on the UI thread while Kestrel runs via `RunAsync`; with no console, stdout is redirected to `data/logs/butterknife.log`. `DesktopLauncher.Run` picks the tray path on Windows bundles and plain `app.Run()` elsewhere. Settings → General shows a Quit button whenever `DesktopLauncher.IsBundled`, which stops the host and therefore also the tray/helper. `dotnet build src/ButterKnife -r win-x64` on macOS/Linux compiles the tray code for checking. The icon source is `packaging/macos/icon.svg`, rendered with headless Chrome to `icon.png` and then to `ButterKnife.icns` (`iconutil`), `packaging/windows/ButterKnife.ico` (csproj `ApplicationIcon`), `wwwroot/favicon.png` and `wwwroot/apple-touch-icon.png`; regenerate all of them together when the SVG changes.

`.github/workflows/release.yml` runs on `v*` tags (and manually): an Ubuntu matrix publishes all four RIDs and uploads them; a Windows job on the `release` environment logs in to Azure with OIDC (`azure/login@v3`, secrets `AZURE_TENANT_ID`/`AZURE_CLIENT_ID`/`AZURE_SUBSCRIPTION_ID`, federated credential on the app registration `butterknife-release` bound to environment `release`) and signs `ButterKnife.exe` with `azure/artifact-signing-action@v2` (account `artifacts-imsuper-fun`, profile `butterknife`, endpoint `https://eus.codesigning.azure.net/`); macOS jobs build the `.app`, then (only when `APPLE_CERTIFICATE_P12` is set, plus `APPLE_CERTIFICATE_PASSWORD`, `APPLE_NOTARY_KEY_ID`, `APPLE_NOTARY_ISSUER_ID`, `APPLE_NOTARY_KEY`) sign the inner executable with the hardened runtime and `packaging/macos/entitlements.plist`, sign the bundle, notarize with `notarytool` and staple, and finally package a `.dmg` (also signed, notarized and stapled); without the secrets the ad-hoc-signed app ships in an unsigned `.dmg`. A release job attaches the zip/dmg/tar.gz files and `SHA256SUMS.txt`. `global.json` pins the SDK to the 10.0 line for `setup-dotnet`. `LICENSE.md` and `THIRD-PARTY-NOTICES.md` are published beside the executable (csproj `None` items with `CopyToPublishDirectory`) and copied into the `.app`'s `Contents/Resources` by the script; when a dependency or vendored library is added, updated or removed, update the notices file (every bundled component is permissive: MIT, BSD, Apache 2.0, public-domain SQLite; nothing copyleft), keeping its copyright line and licence text.

## Manual testing without a real LLM

`.claude/launch.json` has five configurations: `butterknife` (`dotnet run` with the `http` launch profile, port 5175), `butterknife-lan` (port 5175 bound to `0.0.0.0`), `butterknife-fake-llm` (port 5176 so it can run beside a manually started instance, `--no-launch-profile`), which sets `ASPNETCORE_ENVIRONMENT=Development` and points the two seed backends at `http://127.0.0.1:11434` and `http://127.0.0.1:11434/v1` (only matters for an empty database; otherwise add connections under Settings → Connections), `butterknife-test` (port 5177, same seeds, but `Database__ConnectionString=Data Source=data/test.db` so feature verification never touches the real database; delete `src/ButterKnife/data/test.db*` to start fresh) and `butterknife-test-lan` (the same test database on `http://0.0.0.0:5178`: open it at this machine's LAN address, e.g. `http://192.168.x.y:5178/`, to exercise the sign-in page and non-owner accounts, since anything from loopback is always the owner). Pair the latter with `tools/stub-llm-server.py` (`python3 tools/stub-llm-server.py --port 11434 --delay 0.08`), which speaks Ollama (`/api/tags`, `/api/ps`, `/api/show` with `capabilities` — `fake-llama:8b` has `vision`, `fake-tiny:1b` does not —, `/api/chat`), OpenAI-compatible (`/v1/models`, `/v1/chat/completions`, LM Studio's `/api/v0/models/{id}` typing `fake-gpt-vision` as `vlm` and the rest `llm`), Anthropic (`/v1/messages`; `/v1/models` answers in Anthropic shape when `x-api-key` is present) and whisper.cpp (`/inference`; `/v1/audio/transcriptions` returns 404 on purpose) well enough to list models, stream a canned markdown reply with usage/timing fields, and transcribe; it logs the roles and image counts of every request. Every reply starts with "_model_ says:" so side-by-side comparisons can be told apart, streams a few thinking chunks first (Ollama `thinking`; OpenAI `reasoning_content`, or inline `<think>` tags for `fake-gpt`), and ends with inline math, a display equation and a mermaid block. A user message containing `[cut]` gets a reply cut off after six words with a `length` finish; a request whose last message is the assistant's (a Continue) gets a continuation. When a request offers tools (the Code tab) it plays a fixed agent scenario instead, one call per request in each protocol's streaming shape (Ollama whole calls, OpenAI fragments by index, Anthropic `tool_use` + `input_json_delta`): `list_files`, `read_file README.md`, `write_file stub-notes.md`, `edit_file` on it, `run_command ls -la`, then a summary; a prompt containing `[quick]` goes straight to the summary, one containing `[skill]` first calls `read_skill explore-project`, and one containing `[look]` reads `screenshot.png` (a picture, so it comes back as one: put any PNG in the folder), one containing `[bg]` instead starts a six-second background loop, reads it with `command_output`, then runs `mkdir -p src && cd src && pwd` and `pwd` to show the directory sticking. Steps follow the number of calls made since the prompt. Tool replies report a prompt size of the request's JSON length / 4, so a few prompts in a folder with a few-kB README fill `fake-llama:8b`'s 8k window and the Code tab compacts; a request whose system prompt is `CodeCompactor.SummarizerSystemPrompt` gets a fixed two-line summary plus a "Tools called so far: …" line for the latest request, which the stub reads back from the system prompt when a prompt carries `ResentNote`, so its scenario carries on after a compaction inside the turn. To watch that happen, set the Ollama connection's context window to 4096 and work in a folder whose `README.md` is about 9 kB: one prompt compacts twice before the summary. `fake-llama:8b` (Ollama `tools` capability), `fake-gpt` and `fake-gpt-vision` (LM Studio `tool_use`) can call tools, `fake-tiny:1b` cannot; `fake-llama:8b` and `fake-gpt-vision` can also see, which makes them the ones to use for pictures. The stub ignores the moved-pictures user message when counting steps. Raise `--delay` to watch streaming UI. Browser automation note: synthetic "Return" key presses may not reach the textarea's `keydown` listener; dispatch a `KeyboardEvent('keydown', {key: 'Enter'})` from JS instead when scripting the page.

The README screenshot (`docs/screenshots/chat.png`, 1440 × 900, dark) is taken with `node tools/screenshot.mjs <chat url> docs/screenshots/chat.png` against a running instance: the script drives headless Chrome over the DevTools protocol and waits eight seconds before capturing, because Chrome's own `--screenshot` fires on page load, before the circuit connects and the model list arrives (the picker then reads "Loading models…"). Node 22+ (built-in `WebSocket`) and Google Chrome are required; `CHROME=` overrides the browser path.
