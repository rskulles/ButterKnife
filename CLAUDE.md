# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ButterKnife is a .NET Blazor Web App (Server interactivity) for chatting with LLMs hosted on the local network (Ollama, LM Studio, vLLM, llama.cpp server) plus optional Anthropic. The LLM backends are *not* on this machine; every backend is reached over HTTP at a base URL stored in the app's SQLite database.

README.md is written for end users (why, download, connect a server) and deliberately avoids implementation detail; this file is the developer reference.

**Configuration** lives in `src/ButterKnife/appsettings.json` (override per environment file or with `Section__Key` environment variables):

| Section | Keys | Purpose |
|---|---|---|
| `Database` | `ConnectionString` | SQLite file; default `Data Source=data/butterknife.db`, relative to the content root (bundled builds redirect it, see "Releases and the bundled build"). |
| `Llm` | `Backends` | Seed connections, used only when the connections table is empty on first start. Empty in `appsettings.json`; `appsettings.Development.json` seeds two placeholders. |
| `Llm` | `DefaultPersona`, `AutoCompactThreshold`, `CompactKeepRecentTurns` | Persona preselected for new chats; compact when usage passes this fraction of the window (0 disables); turns kept verbatim after a compaction. |
| `Dictation` | `AutoStopOnSilence`, `AutoSendAfterTranscription`, `SilenceDurationMs`, `MaxRecordingSeconds` | Microphone defaults; each browser overrides the two toggles from the ⚙ beside the mic. |

API keys are protected with ASP.NET Core Data Protection. In development the key ring is in the user profile of the account running the app, so running as another user or on another machine makes stored keys read back empty (re-enter them); bundled builds keep the ring beside the database.

**Toolchain.** .NET SDK 10.0, target `net10.0`. `Directory.Build.props` sets `TreatWarningsAsErrors`, nullable and implicit usings for every project, so any analyzer warning fails the build. `.editorconfig` (LF, 4-space indent, 2 for json/yml/slnx) makes file-scoped namespaces and mandatory braces warnings and flags unused usings (IDE0005), all of which therefore fail the build. Client-side libraries are pinned by LibMan (`src/ButterKnife/libman.json`: Bootstrap 5.3.8 JS bundle only, Bootstrap Icons) but the restored files under `wwwroot/lib/` are **committed**, and nothing restores them at build time. Reason: the build-time restore (`Microsoft.Web.LibraryManager.Build`, since removed) ran after static-web-asset discovery on a clean machine, so CI-published builds copied the files but left them out of the endpoints manifest and `MapStaticAssets` returned 404 for the icon font. To update a library, change `libman.json`, run `dotnet tool restore` then `dotnet libman restore` from `src/ButterKnife`, and commit the result. The stylesheet is the Bootswatch "pulse" build committed at `wwwroot/bootstrap_pulse.min.css` (system font stack, no external fetches; the earlier "morph" `bootstrap*.css` files remain in `wwwroot` unreferenced). Icons in markup are `<i class="bi bi-...">`. Solution file is `ButterKnife.slnx` (XML solution format); projects are `src/ButterKnife` (web app) and `tests/ButterKnife.Tests` (xUnit 2.x: no `TestContext`, use `CancellationToken.None`).

## Commands

```bash
# Build / run (dotnet run uses the "http" launch profile: Development environment, http://localhost:5175)
dotnet build
dotnet run --project src/ButterKnife
dotnet watch --project src/ButterKnife        # hot reload during UI work

# Expose on the LAN (Kestrel binds to localhost only by default)
dotnet run --project src/ButterKnife --urls http://0.0.0.0:5175

# Tests
dotnet test
dotnet test --filter "FullyQualifiedName~OllamaClientTests"                       # one class
dotnet test --filter "FullyQualifiedName~OllamaClientTests.StreamsTokensFromNdjson" # one test

# Override seed backends without editing config (env vars use __ as the section separator; seed only, see Connections)
Llm__Backends__0__BaseUrl=http://127.0.0.1:11434 dotnet run --project src/ButterKnife

# Formatting (analyzers run as part of build; warnings are errors)
dotnet format
dotnet format --verify-no-changes

# Offline development against the stub server (see "Manual testing" below)
python3 tools/stub-llm-server.py --port 11434 --delay 0.08
```

## Architecture

**Render mode.** `App.razor` sets `InteractiveServerRenderMode(prerender: false)` on both `Routes` and `HeadOutlet`; `Program.cs` registers only `AddInteractiveServerComponents` / `AddInteractiveServerRenderMode`. Chat needs a live SignalR circuit for token streaming, so do not mix in WebAssembly or Auto modes; there is no client project. Prerendering is off on purpose: the chat page has nothing useful to show statically and prerendering would query every backend's model list twice per page load. The csproj sets `BlazorDisableThrowNavigationException`, so `NavigationManager.NavigateTo` during an interactive handler does not throw. `Components/Layout/ReconnectModal` is the template's reconnect dialog, wired to `Blazor.reconnect` / `resumeCircuit` in its collocated JS.

**DI.** Two extension methods are the only wiring: `Services/LlmServiceCollectionExtensions.AddLlmBackends` (binds and validates `LlmOptions` and `DictationOptions`, registers the shared `"llm"` HttpClient, registry, catalog, markdown renderer, compactor, transcription client/service, and the `ConnectionSeeder` hosted service) and `Data/DataServiceCollectionExtensions.AddDataStores` (`DatabaseOptions`, `SqliteDatabase`, the four stores, `ConversationEvents`, `ConnectionEvents`, `SettingsEvents`). Options classes: `Options/LlmOptions` (`Backends` seed list, `DefaultPersona`, `AutoCompactThreshold`, `CompactKeepRecentTurns`; `BackendKind` is `Ollama` | `OpenAiCompatible` | `Anthropic` | `Transcription`), `Options/DictationOptions`, and `Data/DatabaseOptions` (lives in `Data/`, not `Options/`).

**Layering:**

- `Components/Pages/Chat.razor` (routes `/` and `/chat/{id}`): the chat page, markup and code in one file (the user's IDE copes badly with partial classes, so do not split it again). The `@code` block is sectioned by comment banners: core (state, lifecycle, selection, send/stream), images, context meter + compaction, dictation, and the nested `ChatTurn` transcript entry. The page holds conversation state for the circuit, renders messages, and appends streamed tokens in place via the mutable `ChatTurn` class. Its collocated `Chat.razor.js` module handles Enter-to-send, auto-scroll and dictation; Enter calls back into the component through a `DotNetObjectReference` (`[JSInvokable] SendFromKeyboardAsync`) rather than clicking the Send button, because that button is swapped for a Stop button while streaming and a captured element would go stale.
- **Settings** (`Components/Pages/Settings.razor`, routes `/settings`, `/settings/{Section}` and the legacy `/connections`) uses its own `Components/Layout/SettingsLayout.razor`, which replaces the chat sidebar with a section list (General, Connections, Personas, Data), a "Back to chat" link and the theme toggle; the frame CSS (`.page`, `.sidebar`, `main`) is shared with `MainLayout` from `wwwroot/app.css`. Sections are components under `Components/Settings/`: `GeneralSettings.razor` (display name, LAN switch, PIN, release check, Quit), `ConnectionsSettings.razor` + `.razor.cs` code-behind (the former Connections page, unchanged), `PersonasSettings.razor` and `DataSettings.razor`. App-wide settings are rows in the `settings` table via `Data/ISettingsStore` (`SqliteSettingsStore`; blank value deletes the row), keys and defaults in `SettingKeys`; `SettingsEvents` is the in-process change signal, which `Chat.razor` uses to refresh the label above the user's messages (`SettingKeys.UserDisplayName`, default "User").
- **Network PIN** (Settings → General → "PIN for other devices"): `Services/NetworkPinGate` keeps a salted PBKDF2-SHA256 hash (`SettingKeys.NetworkPinHash`, 100 000 iterations) and a random stamp (`NetworkPinStamp`) regenerated on every set/remove, loaded lazily and reloaded after `SettingsEvents` (a restored backup may carry another PIN). `NetworkPinMiddleware` (`Program.cs`, before antiforgery and the endpoints) lets through requests with a valid `butterknife.unlock` cookie (Data-Protection-protected `stamp|expiry`, 30 days, HttpOnly, SameSite Lax, Secure on https) and everything `NetworkPinGate.IsExempt` names: loopback remote addresses (this computer never needs the PIN, which is also the recovery path when it is forgotten; behind a reverse proxy on the same machine that exemption applies to everyone, so do not put one in front without forwarded headers), the unlock page and any path with a file extension (static assets). Other page requests (GET accepting HTML) are redirected to `/unlock?returnUrl=…`; the rest (`/_blazor` negotiate and websocket, `/backup`, posts) get 401. `NetworkPinEndpoints.MapNetworkPin` serves `/unlock` as a self-contained HTML form (no circuit: the circuit is behind the PIN; it links the plain `/bootstrap_pulse.min.css` path and applies the same `data-bs-theme` logic) and handles its POST: `TryUnlockAsync` verifies the PIN with a per-address counter (five wrong tries lock that address out for a minute), sets the cookie and follows `SafeReturnUrl` (a local path only). Tests cover hashing, validation, tokens and expiry, lockout, exemptions, return URLs and the middleware with a `DefaultHttpContext`.
- **Release check** (Settings → General): `Services/UpdateChecker` (singleton, named HttpClient `github` with a 10 s timeout, registered in `Program.cs`) fetches `https://api.github.com/repos/rskulles/ButterKnife/releases/latest`, parses `tag_name` (`ParseTag`, `v` optional) and compares it with `CurrentVersion` (the assembly's informational version without the `+commit` suffix, i.e. the `-p:Version=` the release workflow passes; 1.0.0 under plain `dotnet run`, so the notice never shows in development; `dotnet run --property:Version=0.1.0` shows it). It runs only when the General section opens, never in the background, caches a successful answer for 6 hours, and reports failures in `UpdateCheck.Error` instead of throwing. The page shows the version, a badge with a Download link to the release when `IsNewer`, or "You have the latest version"; the switch `SettingKeys.CheckForUpdates` ("false" disables; unset means on) turns the check off.
- **Settings → Data** (`Components/Settings/DataSettings.razor`, `/settings/data`) shows the database path and size, a **backup** link and a **restore** upload. Backup is the minimal-API endpoint `GET /backup` in `Program.cs`: `SqliteDatabase.BackupToAsync` writes a consistent snapshot with `VACUUM INTO` to a temp file that is streamed as `ButterKnife-backup-<date>.db` and deleted on close (a plain `<a download>`; Blazor's router leaves links with a `download` attribute alone). Restore copies the uploaded file (`InputFile`, streamed) to a temp path, then `SqliteDatabase.RestoreFromAsync` checks the SQLite header, `PRAGMA quick_check` and the presence of the `conversations`/`messages`/`connections` tables, clears the connection pool, replaces the database file (and `-wal`/`-shm`) under the init lock and resets the schema flag so an older backup gets its migrations on the next open; the page then fires the conversation, connection and settings events. The user confirms before anything is replaced. API keys in a backup are Data-Protection-encrypted for the installation that made it.
- **Open on phone** (`Components/Shared/PhoneLink.razor`, top-left of the chat header, hidden below the `md` breakpoint): a Bootstrap modal toggled from C# (no JS) showing a QR code for the current page at a LAN address. `Services/LanAddressService` builds the candidates: the browser's own host when it is not loopback (e.g. `mac.local`), then the machine's IPv4 addresses (private ranges first, loopback and link-local skipped), each with the page's scheme, port and path; `PhoneAccess.ListensOnLan` (from `IServerAddressesFeature`: a wildcard or non-loopback binding) drives a warning that the server only listens on localhost. The Settings → General switch (`SettingKeys.ListenOnLan`, "true"/"false") is read in `Program.cs` after `Build()`: `Services/ListenAddresses.Apply` rewrites the host part of the configured `urls` (loopback ↔ `0.0.0.0`, ports and schemes kept) into `app.Urls`, which wins over `--urls`/`ASPNETCORE_URLS`; an unset row leaves the configured addresses alone. Kestrel binds at startup, so the page compares the saved switch with the live `ListensOnLan` and shows "restart to apply". The pure `Compute` overload is what the tests exercise. QR codes come from the `QRCoder` NuGet package (`SvgQRCode` with a viewBox, black on white regardless of theme); nothing is fetched from the internet.
- **Transcript actions and streaming** (`Chat.razor`). Messages loaded from the store carry `Id`/`CreatedAt`/`Reasoning` (`ChatMessage` init-only props; `AppendMessageAsync` returns the id) and the transcript entry `ChatTurn` mirrors them (`MessageId`, `CreatedAt`, `Reasoning`, `Finish`, `Stopped`, `ModelName`, `Alternative`). `StreamReplyAsync(conversationId, model, history, continueTurn?)` is the single streaming path used by send, edit-and-resend, regenerate and continue; `StreamIntoAsync` is the store-free core that just fills a turn (also used for the compare-mode shadow turn). Per-message actions appear on hover (`.msg-actions`): edit in place (truncates from that message via `DeleteMessagesFromAsync`, then resends with the same images), regenerate (last reply), continue (when `Finish == Length` or `Stopped`; the history ends with the partial reply, which backends extend; the stored row is rewritten with `SetMessageContentAsync`), copy as Markdown, read aloud (browser `speechSynthesis` over the rendered text, `speakMessage`/`stopSpeaking` in the JS module), branch (`BranchAsync` copies messages up to that one into a new conversation), delete this / this and everything after (inline confirmation). Deleting or truncating clears a compaction summary that no longer fits and resets stored context usage (store rule, mirrored in memory). Stop sets `Stopped` rather than writing "(stopped)" into the text. **Compare mode**: a second model picked in the header (`_compareKey`, session-only) answers each prompt in parallel into `turn.Alternative`, rendered as two columns with "Keep this one"; keeping the alternative calls `ChatTurn.TakeOver` and rewrites the stored reply.
- **Model settings** (sliders button beside the model picker, popover like the dictation one): `Services/ChatOptions(Temperature, MaxTokens, Think)`, null = server default, stored per conversation (`conversations.temperature/max_tokens/think`, `IConversationStore.SetOptionsAsync`, `Conversation.Options`; copied by `BranchAsync`; a new chat keeps them in memory until it is created). `ILlmClient.StreamChatAsync(model, messages, options, ct)` takes them (null for defaults, which is what the titler and compactor pass): Ollama puts temperature/`num_predict` in `options` beside `num_ctx` and `think` at the top level; OpenAI-compatible sends `temperature`, `max_tokens` and, only when Think is set, `chat_template_kwargs.enable_thinking` (what vLLM and llama.cpp honour for Qwen3-style models; others ignore it); Anthropic sends `max_tokens` (default 64000) and `thinking` enabled with a budget of half of max_tokens clamped to 1024–32000, or disabled, and never temperature (current Claude models reject it). The stub server logs the tuning fields of each request.
- **Chat instructions** (header button, panel below the header): free text stored in `conversations.instructions` (`IConversationStore.SetInstructionsAsync`, `Conversation.Instructions`, copied by `BranchAsync`, in memory for a new chat until it exists). `ConversationCompactor.ComposeSystemPrompt(persona, instructions, summary)` puts them after the persona's prompt (with `InstructionsPreamble` when there is a persona, bare otherwise) and before the compaction summary; the two-argument overload remains for callers without instructions. Saving them resets the exact context count so the meter re-estimates. The stub server prints the tail of the system message it receives.
- **Chat titles.** A conversation is created with the first line of the prompt as its title (`MakeTitle`, 60 chars). After the first finished reply, `Services/ChatTitler` asks the same model for a title (`Instruction`: at most six words, title only; prompt and reply excerpts of 1500 chars; inline `<think>` stripped; `Clean` removes quotes, emphasis, a "Title:" prefix and a trailing full stop) and `Chat.razor`'s `SuggestTitleAsync` writes it in the background only if the store still holds the placeholder, so a rename by the user wins. Failures are silent: the placeholder stays. The stub server answers a request starting with that instruction line with a fixed title and no thinking.
- **Export** (header button, `ExportAsync`): `Services/ChatExporter.ToMarkdown` renders the stored conversation (title, export date, model, persona; one `---`-separated section per message with the speaker label and timestamp, an italic image count in place of images, reasoning inside `<details>`), and `ChatExporter.FileName` makes a safe `Title.md`; the JS module's `downloadText` hands the browser a Blob to save.
- **Reasoning.** `ChatDelta` carries `Reasoning` and `Finish` besides text/usage: Ollama `message.thinking` + `done_reason`, OpenAI-style `reasoning_content`/`reasoning` + `finish_reason`, Anthropic thinking deltas + `stop_reason`. Models that think inline as `<think>…</think>` go through `Services/ThinkTagSplitter` in the stream loop (handles tags split across chunks). Reasoning is stored in `messages.reasoning`, shown in a `<details class="msg-thinking">` above the reply (open while thinking, folded once the answer starts, "Thought for Ns"), and never sent back to the model.
- **Reply rendering extras** (JS module, run from `OnAfterRenderAsync` when `_codeBlocksDirty` is set, i.e. after load or a finished reply, never mid-stream): `enhanceCodeBlocks` highlights fenced code with the vendored highlight.js (atom-one-dark, matching the dark code boxes) and adds a copy button (`copyText` uses the Clipboard API in secure contexts and the selection command elsewhere, so it works over plain http from a phone); `enhanceMathAndDiagrams` lazily loads the vendored KaTeX (auto-render over Markdig's `.math` spans/divs) and Mermaid (`pre.mermaid`, `securityLevel: strict`, theme follows colour mode) only when a transcript needs them. Markdig escapes `<` inside mermaid fences, so diagram source cannot inject markup (tested).
- **Images from the clipboard / drag-and-drop** (`wireImageInput`): paste on the composer or drop on the chat frame; files over 1.5 MB or in unusual formats are re-encoded in the browser as a 1568 px JPEG; bytes wait in a JS queue and .NET pulls them with `takeDroppedImage` as an `IJSStreamReference` (a whole image exceeds the SignalR message limit), through `[JSInvokable] OnImagePasted`, subject to the same limits as the picker.
- **Auto-scroll** (`wireScroll`/`scrollToBottom(el, force, streaming)`): the transcript follows streamed text only while `data-pinned="1"`; an upward wheel/touch/key event unpins synchronously (position-based detection alone loses the race against the 50 ms render loop), reaching the bottom re-pins, and a "Jump to latest" pill floats above the transcript's edge while unpinned during a reply. Sending/regenerating/continuing passes `force: true`.
- **Model and stats per reply**: assistant messages store `messages.model` and `messages.stats` (a JSON `GenerationStats` blob, written by `AppendMessageAsync` and updated by `SetMessageContentAsync` when a model/stats are passed; null leaves them). `ChatMessage.Model/Stats` → `ChatTurn.ModelName/StoredStats`; `ChatTurn.DisplayStats` prefers this session's live measurements and falls back to the stored ones, so the stats line and the model name in the speaker line survive a reload. Keeping a compare-mode alternative rewrites the row with that model's name and stats; the exporter labels replies `**Assistant (model)**`.
- **Keyboard shortcuts** (`wireShortcuts`/`unwireShortcuts` in the JS module, wired after `wireInput`, removed in `DisposeAsync`): a document keydown listener sends `OnShortcutAsync("stop")` on Esc (ignored inside other inputs so a rename box keeps its own Esc, and a no-op unless streaming) and `"new-chat"` on Ctrl/⌘+Shift+O; Shift+Esc focuses the composer in JS. Enter/Shift+Enter stay in `wireInput`. The list is shown under Settings → General and in the Send/Stop/New chat tooltips.
- **Timestamps**: `<time>` beside the speaker label, "HH:mm" today or "MMM d, HH:mm", server-local, full date in the tooltip.
- **Throbber and stats.** `Components/Shared/ButterKnifeThrobber` is the animation shown while a reply streams: `wwwroot/throbber.png` is a 56-frame horizontal sprite sheet (32 × 32 px frames) played at 24 fps by a `steps(56)` CSS animation in the scoped stylesheet (the `url()` there is relative to `wwwroot` because scoped CSS is bundled at the site root). It takes a `Func<GenerationStats>` and re-renders itself every 250 ms so the clock runs between tokens. `GenerationStats` (in `Services/ChatDelta.cs`) derives time to first token, prompt rate and generation rate from client-side timings plus the backend's `TokenUsage` (Ollama also reports `prompt_eval_duration`/`eval_duration`). `FormatStats` is the single formatter for both the live readout and the final stats line under each reply.
- **Connections** (`Data/LlmConnection`, `IConnectionStore`, `SqliteConnectionStore`) are the LLM servers, managed at runtime under Settings → Connections (`/settings/connections`) and stored in SQLite. API keys are encrypted at rest with ASP.NET Core Data Protection (`IDataProtector`, purpose `ButterKnife.Connections.ApiKey`); if the key ring changes the key reads back as null and must be re-entered. `Llm:Backends` in config is **seed data only**: `ConnectionSeeder` (hosted service) copies it into the table on first start when the table is empty, then never again. `Services/ConnectionPresets` holds the stock endpoints (Ollama, LM Studio, OpenAI-compatible, Anthropic, Whisper) the page offers. `ConnectionEvents` is an in-process singleton the chat page subscribes to so its model picker refreshes when connections change in another circuit.
- `Services/ILlmClient` is the single abstraction over a connection: `StreamChatAsync` (`IAsyncEnumerable<ChatDelta>`), `ListModelsAsync`, `GetContextWindowAsync`. Implementations are per wire protocol and are built per use by `LlmClientFactory.Create(connection, httpClientFactory)`; `LlmClientRegistry` (`ILlmClientRegistry`) resolves them from the connection store (`GetClientsAsync` filters out non-chat kinds via `LlmClientFactory.IsChatBackend`; `GetAsync(connectionId)` throws `KeyNotFoundException` for a deleted connection):
  - `OllamaClient`: Ollama native API (`api/chat` NDJSON stream, `api/tags`). `BaseUrl` is the server root.
  - `OpenAiCompatibleClient`: `chat/completions` SSE stream and `models`. `BaseUrl` **must include** the version prefix (`…/v1`), matching the OpenAI SDK convention. Covers LM Studio, vLLM, llama.cpp server, and Ollama's `/v1` shim.
  - Both share `LlmClientBase`: one named `HttpClient` (`LlmClientBase.HttpClientName` = `"llm"`, infinite timeout), absolute URIs resolved from `BaseUrl` (a trailing `/` is added so the last path segment such as `v1` is kept), `Bearer` auth when an API key is set, errors surfaced as `LlmException`, `TryGet/TryPostJsonAsync` helpers that return null for optional capability lookups.
  - `AnthropicLlmClient`: the official `Anthropic` NuGet SDK (`AnthropicClient`, `client.Messages.CreateStreaming`, `client.Models.List`). System messages are folded into the request's top-level `System` (the Messages API has no system role); `max_tokens` is 64000; a `refusal` stop reason is surfaced as an error. Tests inject an `HttpClient` into the SDK to stub the wire.
- **Images.** `ChatMessage.Images` holds `ChatImage(MediaType, byte[])` attachments; they are stored in `message_images` (BLOB, cascade on message delete) and re-sent with their message on every turn, so the model sees them in context. Each client encodes them natively: Ollama `images` (raw base64 array on the message), OpenAI-compatible `content` parts (`image_url` data URL, text part first), Anthropic `ImageBlockParam` with a base64 source before the text block. Text-only messages keep `content` as a plain string for compatibility. In `Chat.razor`, `InputFile` reads files over the circuit; files over ~1.5 MB or in unsupported formats are re-encoded in the browser as JPEG bounded to 1568 px via `RequestImageFileAsync`; at most 6 images per message, 10 MB each. `ILlmClient.SupportsImagesAsync(model)` returns true/false/null: Ollama reads `capabilities` (contains `vision`) from `/api/show` (older servers omit the array → null), LM Studio's `/api/v0/models/{id}` `type` (`vlm` → true, `llm` → false), Anthropic is always true, generic OpenAI-compatible servers are null. `Chat.razor` probes the selected model (cached per model key, alongside the context-window probe) and when the answer is **false** it disables the attach button, refuses to send pending images, and replaces every image in the request with a text note via `ChatMessage.WithImagesAsText()` (also for compaction). The stored transcript keeps the images, so switching back to a vision model restores them; null (unknown) sends images as before.
- **Context meter.** `StreamChatAsync` yields `ChatDelta` items: text deltas plus, when the backend reports it, a final `TokenUsage` (Ollama `prompt_eval_count`/`eval_count` on the done chunk; OpenAI-compatible via `stream_options.include_usage` on the last chunk; Anthropic `message_start.usage.input_tokens` + `message_delta.usage.output_tokens`). `GetContextWindowAsync(model)` returns the window or null: Ollama `/api/ps` `context_length` (what a loaded model actually runs with) then `/api/show` `*.context_length`; LM Studio's native `/api/v0/models/{id}` `max_context_length` at the server root; Anthropic Models API `max_input_tokens`. A connection's `ContextWindow` overrides all of that and is sent to Ollama as `options.num_ctx`. `Chat.razor` shows exact usage after a reply (prompt + completion) and a `TokenEstimator` estimate (~4 chars/token, ~1000/image) while typing or before the first reply; values persist on the conversation (`context_tokens`, `context_window`).
- **Compaction** (`Services/ConversationCompactor`) is client-side and backend-agnostic: the model summarises everything older than the last `Llm:CompactKeepRecentTurns` (default 4) turns; the summary is stored on the conversation (`summary`, `summary_through` = number of leading messages it covers) and `ComposeSystemPrompt` folds it into the system prompt of later requests, which then carry only the turns after the checkpoint. The stored transcript is never modified. Auto-compaction runs after a reply when reported usage ≥ `Llm:AutoCompactThreshold` (default 0.8, 0 disables) of a known window; the Compact button does the same on demand. The transcript shows a dashed checkpoint divider with the summary on click.
- **Dictation** (`Services/TranscriptionClient`, `TranscriptionService`). The microphone button in the composer has two paths. If a connection of kind `Transcription` exists (preset "Whisper (speech to text)"), the browser records with `MediaRecorder`, converts the clip to 16 kHz mono PCM WAV with `OfflineAudioContext` (stock whisper.cpp accepts nothing else; every other Whisper server accepts WAV too), .NET pulls the bytes through an `IJSStreamReference` (`takeRecording`) and posts multipart `file` (+ `response_format=json`). `TranscriptionClient` speaks two dialects and remembers per connection which one worked: OpenAI's `audio/transcriptions` under BaseUrl (with `model`), and whisper.cpp's `/inference` at the server root (BaseUrl minus `/v1`; no model field). A 404 on one triggers the other, so users may enter either `http://host:8080` or `http://host:8080/v1`. The text is appended to the textarea. Otherwise `Chat.razor.js` falls back to the Web Speech API (`SpeechRecognition`; Chrome/Edge only, and Chrome sends audio to Google) with interim results streamed to `OnDictation`. Transcription connections are not chat backends: `LlmClientFactory.IsChatBackend` filters them out of the registry and the model picker. While recording, `startMonitor` in the JS module taps the stream with an `AnalyserNode`: it samples the noise floor for 400 ms, treats RMS above ~3× floor as speech, and once speech has been heard stops the recorder after `Dictation:SilenceDurationMs` of quiet (`Dictation:MaxRecordingSeconds` is a hard cap; options validation requires ≥ 300 ms and ≥ 5 s); it also drives the mic button's `--mic-level` glow. `Dictation:AutoStopOnSilence` / `AutoSendAfterTranscription` are server defaults; the ⚙ popover beside the mic overrides them per browser in `localStorage` (`butterknife.dictation`). Test hooks in the JS module: `debugInjectRecording` (run the server path without a microphone), `debugUseSyntheticMicrophone` (a tone-then-silence stream for the detector), `debugState`, `debugConvertTone`.
- `Services/ModelCatalog` fans out to every chat connection for its model list; a connection that is down is returned in `Unreachable` (`UnreachableConnection(ConnectionId, ConnectionName, Message)`) rather than failing the whole call. The chat page's model picker groups models by connection (`<optgroup>`) once more than one connection is involved and lists each unreachable connection as a greyed-out group with the error; a conversation whose saved model lives on an unreachable connection keeps that model selected (a disabled option) with Send disabled, instead of being moved to another box (`ReconcileSelection` only swaps in the default when the model or connection is really gone). `ModelDescriptor` is keyed by `connectionId::model` and carries `IsDefault` (matches the connection's `DefaultModel`).
- `Services/MarkdownRenderer`: Markdig pipeline (advanced extensions, `DisableHtml()`) used to render assistant replies as `MarkupString`. Raw HTML is disabled deliberately: model output is untrusted and would otherwise be injected into the page. User messages are rendered as plain text. `ChatTurn` caches the rendered HTML until the next token arrives, so throttled re-renders during streaming do not re-parse older messages.

**Key constraints:**

- HTTP-based clients go through the `IHttpClientFactory` named client `"llm"`; never `new HttpClient()`. Clients call `CreateClient` per request (not cached) so handler rotation keeps working. Timeout is `Timeout.InfiniteTimeSpan`; cancellation comes only from the caller's `CancellationToken`.
- Request bodies are serialised to a `StringContent` up front so they carry a `Content-Length`; some thin proxies and minimal servers cannot read chunked request bodies.
- Streaming must honour cancellation. The `CancellationToken` passed into `ILlmClient` is tied to the user's "Stop" button and to circuit disconnect; every `await` in the streaming path must forward it.
- Colour mode is Bootstrap's `data-bs-theme` on `<html>`, applied by an inline script in `App.razor` before the stylesheets load (choice in `localStorage` key `butterknife.theme`: `light` | `dark` | `auto`; `window.butterKnifeTheme.get/set`). `Components/Shared/ThemeToggle.razor` is the UI, placed in the sidebar footer beside the Settings link (`NavMenu.razor`) and in the settings layout's footer; there is no top bar in either layout. All app CSS must use Bootstrap variables (`var(--bs-...)`) rather than literal colours so both modes work; the template's hardcoded overrides in `wwwroot/app.css` were removed for that reason. Prefer Bootstrap utility classes over new custom CSS.
- Scoped CSS (`*.razor.css`) does not reach elements rendered by child components such as `NavLink`; use `::deep` for those (see `NavMenu.razor.css`).
- Blazor Server UI updates from a streaming loop must call `InvokeAsync(StateHasChanged)`. `Chat.razor` throttles to one render per 50 ms (`RenderInterval`) rather than re-rendering on every token.
- Conversations are persisted server-side through `Data/IConversationStore` (SQLite via `SqliteConversationStore`, plain ADO.NET). The `backend` column holds the **connection id** (GUID string); rows from before connections existed hold a name and resolve to `Guid.Empty`, so the chat shows "model no longer available" until the user picks one. The DB path comes from `Database:ConnectionString` (default `Data Source=data/butterknife.db`, relative to the content root). On case-insensitive filesystems (macOS, Windows) `data/` **is** the `Data/` source folder, so `.gitignore` excludes `src/ButterKnife/data/*.db*` by file rather than the folder; a folder rule silently hides new `Data/*.cs` files from `git status`. `Chat.razor` serves both `/` and `/chat/{id}`: the first send creates the conversation and navigates to its URL with `replace: true`, and `OnParametersSetAsync` reloads only when the id actually changes. Load order matters: `OnInitializedAsync` awaits only local data (personas, display name) and starts the model list in the background (`RefreshModelsInBackgroundAsync`), because `ModelCatalog` waits on every connection and a dead one blocks for the TCP connect timeout; the transcript therefore renders first with the saved model key selected, and `ReconcileSelection` (called when the list lands and on conversation load) swaps in the default with a note if that model no longer exists. While the list is empty the picker binds the placeholder option rather than the saved key. The user message is saved before the request goes out; the assistant reply (or the partial text after Stop / disconnect) is saved when streaming ends. `ConversationEvents` is an in-process singleton the sidebar (`NavMenu.razor`) and chat page subscribe to so the list refreshes across circuits. **Pin and archive**: `conversations.pinned`/`archived` flags (`SetPinnedAsync`/`SetArchivedAsync`, no `updated_at` touch), `ListAsync` orders pinned first then newest, `ConversationSummary` carries both flags; the sidebar row (a `RenderFragment<ConversationSummary>` in `NavMenu.razor`) has a Bootstrap dropdown (`data-bs-popper-config` fixed strategy so the scrolling list does not clip it) with Pin/Rename/Archive/Delete, and archived chats sit under a folded "Archived (n)" toggle at the end of the list.
- System prompts come from **personas** (`Data/Persona`, `IPersonaStore`, `SqlitePersonaStore`). A conversation stores only `persona_id`; the persona's prompt is looked up at request time and prepended as a `ChatRole.System` message, never stored as a message row and never shown in the transcript. Built-in personas live in `DefaultPersonas.All` with **stable ids** (never change or reuse one) and are seeded with `INSERT OR IGNORE`, so users can edit them and edits survive restarts; they cannot be deleted. Custom personas are ordinary rows (`is_builtin = 0`) and deleting one sets `persona_id` to NULL on its conversations. `Llm:DefaultPersona` names the persona preselected for new chats. Settings → Personas (`Components/Settings/PersonasSettings.razor`, `/settings/personas`) lists them (built-in/custom badges), adds custom ones, edits any (a built-in whose text differs from `DefaultPersonas.All` offers "Restore original"), and deletes custom ones after an inline confirmation; `Data/PersonaEvents` tells open chat pages to reload their picker (a chat whose persona was deleted drops to none, matching what the store did to the row).
- `SqliteDatabase` owns the connection string, schema creation (`CREATE TABLE IF NOT EXISTS`), seeding and forward-only migrations: columns added after first release go through `AddColumnIfMissingAsync`, never by editing the `CREATE TABLE`. All stores take it by constructor and open a connection per operation. Circuit state holds only what the page is showing; everything durable goes through a store.
- `Llm:Backends` in `appsettings*.json` only seeds an empty database; keep committed defaults to placeholders like `http://ollama.local:11434`. `appsettings.Development.json` *replaces* the `Backends` array index-by-index, it does not merge.
- The app is intended to be reachable from other devices on the LAN. The Settings switch above or `--urls`/`ASPNETCORE_URLS` bind to `0.0.0.0`; the SignalR circuit requires WebSockets, so any reverse proxy in front must forward `Upgrade` headers. Browser microphone access needs a secure context, so dictation from another device needs TLS.

## Tests

`tests/ButterKnife.Tests` is xUnit with no web host. Conventions worth reusing:

- `StubHttp.cs`: `StubHandler` (an `HttpMessageHandler` that records `LastRequest`/`LastRequestBody`) with factories `Text(body)`, `Route({"GET /api/tags": ...})` (404 for unmatched paths) and `NeverEnding(prefix)` (streams then blocks until cancelled, for cancellation tests); `StubClientFactory(handler, baseUrl)` wraps one as an `IHttpClientFactory`. The bodies in these tests are the exact wire shapes each backend is expected to produce.
- `TestConnections.Make(name, kind, baseUrl, ...)` builds an `LlmConnection`; `ToTextListAsync()` / `LastUsageAsync()` on an `IAsyncEnumerable<ChatDelta>` split text from usage.
- Store tests construct `SqliteDatabase` against a temp directory (`Data Source=<tmp>/nested/test.db`) and delete it in `Dispose`; they also open raw `SqliteConnection`s to assert on schema and rows.
- `ThrobberStatsTests` cover `GenerationStats` and `ButterKnifeThrobber.FormatStats`; `DictationOptionsTests` cover option validation.

## Releases and the bundled build

`dotnet publish -r <rid>` produces a self-contained single-file executable (csproj `PropertyGroup` conditioned on `RuntimeIdentifier`: `SelfContained`, `PublishSingleFile`; trimming stays off because Blazor Server and the SDKs use reflection). `EnableCompressionInSingleFile` is on for Windows and Linux but **off for macOS**: with the hardened runtime on macOS 26 a compressed bundle dies with AccessViolations in framework code (R2R images decompressed into anonymous executable memory lose execute permission on thread-pool threads) on the first browser load, reproduced 11 of 12 launches against 0 of 6 uncompressed using `tools/browser-sim.py` (page + parallel assets + SignalR websocket); the `.dmg` is compressed so the download size is unchanged. Do not turn it back on for macOS without re-running that test on a Developer-ID-signed build. `IncludeNativeLibrariesForSelfExtract` is deliberately **false**: SQLite's `e_sqlite3` native library is published beside the executable (`libe_sqlite3.dylib` / `e_sqlite3.dll` / `libe_sqlite3.so`) instead of being extracted to `~/.net/<app>/<id>/` on first start. Extraction is shared by every copy of the same build and an interrupted first launch leaves it corrupt, after which every start dies with an AccessViolation in the thread pool (reproduced with kill -9 during start-up); shipping the file also lets it be signed and notarized with the bundle. `tools/make-macos-app.sh` copies `*.dylib` into `Contents/MacOS` and the workflow signs them; the Windows signing step's filter is `exe,dll`. `Services/DesktopLauncher` detects that bundle at runtime (`Assembly.Location` is empty in a single-file app; IL3000 is suppressed on that line on purpose) and only then: makes `AppContext.BaseDirectory` the content root so `wwwroot/` and `data/` sit beside the executable, persists Data Protection keys to `data/keys` (DPAPI-wrapped on Windows) so stored API keys survive moving the folder, defaults the listen address to `http://localhost:5175` when nothing is configured (5000 collides with macOS AirPlay), logs the local and LAN URLs, and opens the browser unless `BUTTERKNIFE_NO_BROWSER` is set. `dotnet run` never takes that path, so the development database stays in `src/ButterKnife/data/`. `appsettings.json` seeds no connections; only `appsettings.Development.json` does. On macOS the release is a `.app` built by `tools/make-macos-app.sh` from the publish folder: executable in `Contents/MacOS`, `wwwroot`/`appsettings.json`/static-assets manifest in `Contents/Resources` (`DesktopLauncher.IsMacAppBundle` detects the `Contents/MacOS` location and points the content root, the static-assets manifest path passed to `MapStaticAssets`, and the data directory accordingly). A signed bundle must never be written to, so in a `.app` the database and key ring live in `~/Library/Application Support/ButterKnife`. `Info.plist` sets `LSUIElement` (no Dock icon) and names `ButterKnifeMenu` as the main executable: a Swift menu bar helper (`packaging/macos/ButterKnifeMenu/main.swift`, compiled by the script with `swiftc -target <arch>-apple-macos12.0`) that launches `Contents/MacOS/ButterKnife` with `BUTTERKNIFE_NO_BROWSER=1`, tails its stdout into `~/Library/Logs/ButterKnife/server.log`, parses the "ButterKnife is running at X (on your network: Y)" line for the Open / Copy-address items and the first browser open, sends SIGTERM (then SIGKILL after 5 s) on Quit, routes SIGTERM/SIGINT/SIGHUP to itself through the same quit, and exits when the server exits on its own. It also passes `BUTTERKNIFE_PARENT_PID`; `DesktopLauncher.WatchParent` polls that pid every 2 s and stops the host if it vanishes, so a crashed helper cannot leave an orphaned server. **Windows** release builds are the same project compiled under `net10.0-windows` (csproj group conditioned on a `win*` RID: `UseWindowsForms`, `OutputType WinExe`, `EnableWindowsTargeting` so Linux CI can build it); `Services/WindowsTray.cs` is inside `#if WINDOWS` and pumps a `NotifyIcon` (Open, Copy address, Quit) on the UI thread while Kestrel runs via `RunAsync`; with no console, stdout is redirected to `data/logs/butterknife.log`. `DesktopLauncher.Run` picks the tray path on Windows bundles and plain `app.Run()` elsewhere. Settings → General shows a Quit button whenever `DesktopLauncher.IsBundled`, which stops the host and therefore also the tray/helper. `dotnet build src/ButterKnife -r win-x64` on macOS/Linux compiles the tray code for checking. The icon source is `packaging/macos/icon.svg`, rendered with headless Chrome to `icon.png` and then to `ButterKnife.icns` (`iconutil`), `packaging/windows/ButterKnife.ico` (csproj `ApplicationIcon`), `wwwroot/favicon.png` and `wwwroot/apple-touch-icon.png`; regenerate all of them together when the SVG changes.

`.github/workflows/release.yml` runs on `v*` tags (and manually): an Ubuntu matrix publishes all four RIDs and uploads them; a Windows job on the `release` environment logs in to Azure with OIDC (`azure/login@v3`, secrets `AZURE_TENANT_ID`/`AZURE_CLIENT_ID`/`AZURE_SUBSCRIPTION_ID`, federated credential on the app registration `butterknife-release` bound to environment `release`) and signs `ButterKnife.exe` with `azure/artifact-signing-action@v2` (account `artifacts-imsuper-fun`, profile `butterknife`, endpoint `https://eus.codesigning.azure.net/`); macOS jobs build the `.app`, then (only when `APPLE_CERTIFICATE_P12` is set, plus `APPLE_CERTIFICATE_PASSWORD`, `APPLE_NOTARY_KEY_ID`, `APPLE_NOTARY_ISSUER_ID`, `APPLE_NOTARY_KEY`) sign the inner executable with the hardened runtime and `packaging/macos/entitlements.plist`, sign the bundle, notarize with `notarytool` and staple, and finally package a `.dmg` (also signed, notarized and stapled); without the secrets the ad-hoc-signed app ships in an unsigned `.dmg`. A release job attaches the zip/dmg/tar.gz files and `SHA256SUMS.txt`. `global.json` pins the SDK to the 10.0 line for `setup-dotnet`. `LICENSE.md` and `THIRD-PARTY-NOTICES.md` are published beside the executable (csproj `None` items with `CopyToPublishDirectory`) and copied into the `.app`'s `Contents/Resources` by the script; when a dependency or vendored library is added, updated or removed, update the notices file (every bundled component is permissive: MIT, BSD, Apache 2.0, public-domain SQLite; nothing copyleft), keeping its copyright line and licence text.

## Manual testing without a real LLM

`.claude/launch.json` has four configurations: `butterknife` (`dotnet run` with the `http` launch profile, port 5175), `butterknife-lan` (port 5175 bound to `0.0.0.0`), `butterknife-fake-llm` (port 5176 so it can run beside a manually started instance, `--no-launch-profile`), which sets `ASPNETCORE_ENVIRONMENT=Development` and points the two seed backends at `http://127.0.0.1:11434` and `http://127.0.0.1:11434/v1` (only matters for an empty database; otherwise add connections under Settings → Connections), and `butterknife-test` (port 5177, same seeds, but `Database__ConnectionString=Data Source=data/test.db` so feature verification never touches the real database; delete `src/ButterKnife/data/test.db*` to start fresh). Pair the latter with `tools/stub-llm-server.py` (`python3 tools/stub-llm-server.py --port 11434 --delay 0.08`), which speaks Ollama (`/api/tags`, `/api/ps`, `/api/show` with `capabilities` — `fake-llama:8b` has `vision`, `fake-tiny:1b` does not —, `/api/chat`), OpenAI-compatible (`/v1/models`, `/v1/chat/completions`, LM Studio's `/api/v0/models/{id}` typing `fake-gpt-vision` as `vlm` and the rest `llm`), Anthropic (`/v1/messages`; `/v1/models` answers in Anthropic shape when `x-api-key` is present) and whisper.cpp (`/inference`; `/v1/audio/transcriptions` returns 404 on purpose) well enough to list models, stream a canned markdown reply with usage/timing fields, and transcribe; it logs the roles and image counts of every request. Every reply starts with "_model_ says:" so side-by-side comparisons can be told apart, streams a few thinking chunks first (Ollama `thinking`; OpenAI `reasoning_content`, or inline `<think>` tags for `fake-gpt`), and ends with inline math, a display equation and a mermaid block. A user message containing `[cut]` gets a reply cut off after six words with a `length` finish; a request whose last message is the assistant's (a Continue) gets a continuation. Raise `--delay` to watch streaming UI. Browser automation note: synthetic "Return" key presses may not reach the textarea's `keydown` listener; dispatch a `KeyboardEvent('keydown', {key: 'Enter'})` from JS instead when scripting the page.

The README screenshot (`docs/screenshots/chat.png`, 1440 × 900, dark) is taken with `node tools/screenshot.mjs <chat url> docs/screenshots/chat.png` against a running instance: the script drives headless Chrome over the DevTools protocol and waits eight seconds before capturing, because Chrome's own `--screenshot` fires on page load, before the circuit connects and the model list arrives (the picker then reads "Loading models…"). Node 22+ (built-in `WebSocket`) and Google Chrome are required; `CHROME=` overrides the browser path.
